## 網路限速器 ( Rate Limiter )
- HTTP 世界裡網路限速器可以用來限制客戶端在指定時間內發送請求的數量
- ex: 每秒只能發兩則貼文, 同 IP 只能創建 5 次帳號....

---

## 網路限速器的好處
- 避免 DoS ( Denial of Service )
- 降低成本
- 防止是伺服器超載

## Token桶 ( Token bucket )
- 它簡單易懂，常被網路公司採用。 Amazon 和 Stripe都使用這個演算法來限制他們的 API 請求。
- 原理:
    - 有一個固定容量的容器，定期放 token 進去，滿了就不放。
    - 每個 request 消耗一個 token ， token 沒了就不給 request

## 桶的設計
- 通常需要為不同的API端點使用不同的桶子。例如，如果一個用戶被允許每秒發1個帖子，每天添加150個好友，並且每秒鐘點讚5個帖子，則每個用戶需要3個桶。

- 如果我們需要根據IP位址對請求進行限流，每個IP位址都需要一個桶。
- 如果系統允許每秒最多10,000個請求，則有一個全域桶供所有請求共用是有意義的。

---

- 優點
    - 演算法容易實現
    - 佔用記憶體少
    - 令牌桶允許在短時間內進行突發流量。只要有剩餘的令牌，請求就可以通過。
- 缺點
    - 演算法中有兩個參數，即桶的大小和令牌的補充速率。然而，正確調整它們可能具有挑戰性。

---

## 漏水桶 ( Leaking bucket )
- 演算法與 token桶類似，不同之處在於請求是以固定速率處理的。它通常用先入先出（FIFO）佇列來實作。

- 該演算法的工作原理如下：
    - 當請求到達時，系統會檢查佇列是否已滿。如果佇列未滿，則將請求新增至佇列。否則，將丟棄該請求。
    - 請求會在固定的時間間隔內從佇列中取出並進行處理。

---

![image](https://hackmd.io/_uploads/Bk2LB47-Jx.png)

---

- 漏水桶演算法需要以下兩個參數
    - 桶的大小：它等於佇列的大小。隊列容納了要以固定速度處理的請求。
    - 流出率：定義了在固定速率下可以處理多少請求，通常以秒為單位。
- Shopify，一家電子商務公司，使用漏水桶來限制速度。

---

- 優點：
    - 鑑於隊列大小有限，記憶體效率高。
    - 請求以固定的速率處理，因此它適用於需要穩定流出速率的用例。
- 缺點：
    - 突發的流量使佇列充滿了舊的請求，如果這些請求沒有及時處理，最近的請求將受到速率限制。
    - 演算法中有兩個參數，要適當地調整它們可能並不容易。

---

## 固定視窗計數器 ( Fixed window counter )
- 工作原理如下：
    - 該演算法將時間軸劃分為固定大小的時間窗口，並為每個窗口分配一個計數器。
    - 每個請求將計數器增加一。
    - 一旦計數器達到預定的閾值，新的請求就會被放棄，直到新的時間視窗開始。

## 滑動視窗日誌紀錄 ( Sliding window log )
- 優化固定窗口法
- 該演算法對請求的時間戳進行追蹤。時間戳資料通常保存在快取中，如Redis的sorted。
- 當一個新的請求進來時，刪除所有過期的時間戳記。過時的時間戳被定義為比當前時間視窗的開始時間更早的時間戳記。
- 將新請求的時間戳記新增至日誌中
- 如果日誌大小與允許的計數相同或更低，則接受請求。否則，它將被拒絕

---

- 允許數量為 2
![image](https://hackmd.io/_uploads/rJ505SmW1l.png)

---

- 優點：
    - 這種演算法實現的速率限制是非常準確的。在任何捲動視窗中，請求都不會超過速率限制。
- 缺點：
    - 該演算法消耗了大量的內存，因為即使一個請求被拒絕，其時間戳仍可能被存儲在內存中


---

## 滑動視窗計數器 ( Sliding window counter )
- 結合前兩種演算法，該演算法可以透過兩種不同的方法來實現。我們將在本節中解釋一種實作方法，並在本節末尾提供另一種實作方法的參考。

---

![image](https://hackmd.io/_uploads/S17QulBWyg.png =70%x)
- 目前視窗中的請求數量 + 上一個視窗中的請求數量 * 捲動視窗和上一個視窗的重疊百分比
- 使用這個公式，我們得到3+5×0.7 = 6.5 個請求。

---

- 優點：
    - 它平滑了流量的峰值，因為速率是基於前一個視窗的平均速率。
    - 記憶體高效
- 缺點：
    - 它只適用於不太嚴格的回看視窗。它是實際速率的近似值，因為它假設前一個視窗的請求是均勻分佈的。然而，這個問題可能不像它看起來那麼糟糕。 根據Cloudflare 所做的實驗，在4億個請求中，只有0.003%的請求被錯誤地允許或限制速率

---

## 高階架構
- 限流演算法的基本想法很簡單。在高層次上，我們需要一個計數器來追蹤來自同一用戶、IP位址等的多少個請求。如果計數器大於限制值，則請求被禁止。
- 由於磁碟存取速度慢，使用資料庫並不是一個好主意。選擇記憶體快取是因為它速度快並且支援基於時間的過期策略。 例如，Redis是實現速率限制的一個流行選擇。它是一個記憶體中的存儲。

---

1. 客戶端向限流中間件發送請求
2. 限流中間件從Redis中對應的桶中取得計數器，並檢查是否達到限制
3. 如果達到限制，則拒絕該請求
4. 如果沒有達到限制，請求會被傳送到API伺服器。同時，系統會增加計數器並將其儲存回Redis。

## [Lyft](https://zh.wikipedia.org/zh-tw/%E6%9D%A5%E7%A6%8F%E8%BD%A6) 的速率限制元件。
```
domain: messaging
descriptors:
  - key: message_type
    Value: marketing
    rate_limit:
      unit: day
      requests_per_unit: 5
```
- 在上述例子中，系統被配置為每天最多允許5個行銷訊息。

---

- 客戶不允許在1分鐘內登入超過5次。規則一般寫在設定檔中並保存在磁碟上。
```
domain: auth
descriptors:
  - key: auth_type
    Value: login
    rate_limit:
      unit: minute
      requests_per_unit: 5
```

## 超過速率限制
- 如果一個請求被限制了速率，API會向客戶端回傳一個HTTP回應碼429（請求太多）。
- 根據不同的使用情況，我們可能會將速率受限的請求排隊等候以後處理。 
- 例如，如果一些訂單因係統過載而受到速率限制，我們可以保留這些訂單以便日後處理。

---

## 限流器請求頭
- 限流器向客戶端傳回以下 HTTP 標頭：
    - X-Ratelimit-Remaining：視窗內允許請求的剩餘數量
    - X-Ratelimit-limit：它表示客戶端在每個時間視窗可以進行多少次調用
    - X-Ratelimit-Retry-After：等待的秒數，直到你可以再次提出請求而不被節流。
- 當使用者發送過多請求時，將向客戶端傳回 429 too many requests 和 X-Ratelimit-Retry-After。

## 分散式環境下的限流器
- 建立一個在單一伺服器環境下運行的限流器並不困難。將系統擴展到支援多個伺服器和並發線程是另一回事。
- 這裡有兩個挑戰：
    - 競爭條件
    - 同步問題

---

## 競爭條件
- 如前所述，限流器在高層的工作原理如下
    1. 從Redis讀取計數器的值
    2. 檢查 ( 計數器 + 1 ) 是否超過閾值
    3. 如果不是，則將 Redis 中的計數器值加 1

---

![image](https://hackmd.io/_uploads/rke-SZBZJx.png)

---

- 鎖定是解決競爭條件最明顯的解決方案。 
- 但是，鎖會顯著降低系統速度。 通常使用兩種策略來解決這個問題： 
    - Lua 腳本 
    - Redis 中的 sorted sets 資料結構。 

---

## 同步問題
- 這是分散式環境中要考慮的另一個重要因素。 
- 要支援數百萬用戶，一個限流器伺服器可能不足以處理流量。
- 當使用多個限流器伺服器時，需要同步。 
- 例如，在圖 4-15 的左側，客戶端 1 將請求傳送到限流器 1，客戶端 2 將請求傳送到限流器 2。 由於 Web 層是無狀態的，客戶端可以將請求傳送到不同的限流器，如圖所示，在圖 4-15 的右側。 如果沒有發生同步，限流器 1 不包含任何關於客戶端 2 的資料。因此，限流器無法正常運作。

---

- 左圖，客戶端1將請求傳送到限流器1，客戶端2將請求傳送到限流器2。由於 Web 層是無狀態的，客戶端可以將請求傳送到不同的限流器，右圖。 如果沒有發生同步，限流器 1 不包含任何關於客戶端 2 的資料。因此，限流器無法正常運作。

- 一種可能的解決方案是使用黏性會話( sticky session )，允許客戶端將流量傳送到相同的限流器。這個解決方案是不可取的，因為它既不可擴展也不靈活。

## 效能最佳化
- 效能最佳化是系統設計面試中的一個常見主題。
- 我們將涉及兩個方面的改進：
    - 多資料中心的設定對限流器至關重要，因為對於遠離資料中心的使用者來說，延遲很高。流量會自動路由到最近的邊緣伺服器，以減少延遲。( 邊緣計算 )
    - 用一致性模型來同步資料。如果你不清楚最終的一致性模型，這邊伏筆埋給第六章的講者。

---

## 監控
- 限流器到位後，最重要的是要收集分析資料以檢查限流器是否有效。
- 要確保限流演算法是有效的&限流規則是有效的
- 如果速率限制規則過於嚴格，則會丟棄許多有效請求。在這種情況下，我們想稍微放寬規則。 
- 在另一個例子中，我們注意到當流量突然增加時（如搶購），我們的限流器變得無效。在這種場景下，我們可能會更換演算法來支援突發流量。 Token 桶很適合這種場景。

## 網路限速器的硬性限制 vs 軟性限制
- 硬性限制: 請求數完全不能超過門檻
- 軟性限制: 短時間內允許超過門檻

## 避免被限速，使用最佳實踐設計你的客戶端
- 使用客戶端快取，以避免頻繁呼叫API
- 了解速度限制，不要在短時間內發送太多請求
- 捕獲異常或錯誤的程式碼，以便用戶端可以從異常中恢復正常
- 為 retry 邏輯增加足夠的間格時間 ( backoff time )
