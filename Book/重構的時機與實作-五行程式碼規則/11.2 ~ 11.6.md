# Ch11.2.2 在資料結構中表述行為
- 讓程式碼反應行為的三種方式
    1. 在控制流程中
    2. **在資料的結構中**
    3. 在資料本身
- 資料結構就像是凍結在時間中的演算法
- [BST ( Binary Search Tree )](https://www.cs.usfca.edu/~galles/visualization/BST.html)
    - 每次比較可捨去半邊的串列
- 用型別定義無窮迴圈
```javascript
class Rec {
    Constructor(public readonly f: (_: Rec) => void) {}
}
function loop(){
    let helper = (r: Rec) => r.f(r);
    helper(new Rec(helper));
}
```

# Ch11.2.3 在資料中表述行為
- 最困難，因為會遇到工具和編譯器的停機問題盲點
- 無窮迴圈
    - 使用參照的方式 => 尋找參照的函示尋找參照 -> 找到自己
    - 透過 heap 間接進行 -> heap-buffer-overflow
```javascript
function loop(){
    let a = [() => {}];
    a[0] = () => a[0]();
    a[0]();
}
```

# 11.3 新增程式碼來揭開結構

- 重構是為了支持特定的變更向量，因此程式碼越多越可能知道程式碼變動方向
- 重構會讓程式碼更穩固，改起來更方便
- 如果在存在很多不確定性的系統中，需要的是實驗而不是穩定性 -> 使用列舉和迴圈比使用類別合理，因為改動比較快速，等到穩定後再重構
# 11.4 觀察而非預測，並使用經驗技術

- 預測變更方向重構可能會造成日後修改困難
- 透過實證技術和結構化實驗來持續改進，例如: 豐田模式，以證據為基礎的管理和爆米花流程
![image](https://hackmd.io/_uploads/B10mcf-7A.png)
- 別自作聰明去重構不會改變的東西甚至直接寫死也沒問題，例如五子棋遊戲
- 觀察程式碼變化趨向
    - 如果程式碼沒變動，就不做事
    - 如果難以預測需求，只要重構避免脆弱
    - 否則，只要重構讓他可以適應已經發生過的類型
# 11.5 不用理解程式碼就能取得安全性

- 不須理解方法內部運作，並遵循正確的重構模式就好
## 11.5.1 透過測試取得安全性

- 測試各種可能的 case
## 11.5.2 透過掌控取得安全性

- 把步驟切碎，並且練習

## 11.5.3 透過工具輔助取得安全性

- 透過 IDE 來輔助完成 重構 combo

## 11.5.4 透過正式的驗證取得安全性

- 正式驗證
- ESLint -> 找潛在問題
## 11.5.5 透過容錯取得安全性

- feature toggling
- auto rollback
- error handle or 防呆
